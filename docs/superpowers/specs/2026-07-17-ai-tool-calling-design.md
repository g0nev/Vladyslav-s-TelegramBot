# ИИ с tool calling для /ask — дизайн

## Контекст

`/ask` (Task, добавленный после основного плана бота) сейчас — простая обёртка над OpenRouter: текст вопроса уходит в модель (Llama 4 Scout по умолчанию), ответ пересылается как есть. Модель не может ничего сделать в чате — только сгенерировать текст.

Цель этой фичи: дать `/ask` возможность **выполнять существующие действия бота** (управление триггер-словами, предупреждениями, рассылкой, текстами наказаний, вплоть до мьюта/кика) по запросу на естественном языке — но так, чтобы модель не могла обойти уже существующую систему прав, и чтобы обычный участник не мог таким образом получить доступ к админ-действиям.

Расширение самого набора slash-команд (pin/unpin, lock чата, инвайт-ссылки и т.п.) **не входит** в этот дизайн — по решению пользователя это отдельный будущий шаг. ИИ получает доступ к 13 существующим админ-командам и 1 существующей открытой команде (`/warns`/`/listwords`/`/listmsgs`), плюс к прямому мьюту/кику по просьбе админа — это не отдельная slash-команда, а новая возможность: сейчас мьют/кик происходят только автоматически при накоплении нарушений (`moderation/handlers.py`), а не по прямому запросу админа. Логика мьюта/кика для ИИ выносится в отдельный переиспользуемый модуль (см. ниже), не связанный со счётчиком нарушений.

## Источник паттерна безопасности

В соседнем проекте пользователя (AuraSynk) для похожей проблемы (модель может «сломаться» под давлением и нарушить правило из системного промпта) используется **детерминированный regex-фильтр**, который проверяет текст пользователя ДО обращения к модели и, если совпадение найдено, возвращает заготовленный ответ, вообще не вызывая LLM (`checkHardBlock()` в `src/lib/content-filter.ts`, вызывается в `handleChatStream` до списания баланса и до `fetch` к OpenRouter). Модель физически не видит заблокированное сообщение — её нельзя «уговорить», потому что она не участвует в этом шаге.

Мы используем тот же принцип для двух вещей:
1. **Доступность инструментов по правам** — модели просто не передаётся описание инструмента, если вызывающий не админ (уже само по себе как фильтр AuraSynk: решение принимает код, а не модель).
2. **Разрешение цели действия** — для мьюта/кика/сброса предупреждений целевой пользователь берётся из `reply_to_message` (детерминированно), а не подбирается моделью по имени из текста.
3. **Новый regex hard-filter** (по аналогии) — отдельная проверка текста вопроса на попытки манипуляции самой моделью (prompt injection), до вызова OpenRouter.

## Архитектура

### Поток `/ask`

```
question = command.args
1. check_hard_block(question) → если True: ответить отказом, СТОП (без вызова OpenRouter)
2. is_admin(bot, chat_id, user_id) → выбрать набор инструментов: PUBLIC_TOOLS или ADMIN_TOOLS
3. reply_to_message есть? → запомнить target_user_id/target_mention для инструментов, которым нужна цель
4. ask_ai_with_tools(question, tools) → либо текстовый ответ, либо запрос на вызов инструмента
5a. Текстовый ответ → переслать как есть (как сейчас)
5b. Запрос на инструмент, требующий цель (reply), но reply отсутствует → сообщить "ответьте на сообщение нужного человека", СТОП
5c. Запрос на mute_user/kick_user → отправить сообщение с inline-кнопками "✅ Да" / "❌ Отмена", выполнить действие только по нажатию "Да" (проверив, что нажал тот же админ, который вызвал /ask)
5d. Любой другой инструмент → выполнить сразу через Repository/Bot, ответить коротким подтверждением
```

### Набор инструментов

**PUBLIC_TOOLS (доступны всем участникам чата):**
| Инструмент | Аргументы | Реализация |
|---|---|---|
| `list_trigger_words` | — | `repository.list_trigger_words(chat_id)` |
| `get_user_warnings` | — (цель из reply, обязателен) | `repository.get_warning(chat_id, target_id)` |
| `list_broadcast_messages` | — | `repository.list_broadcast_messages(chat_id)` |

**ADMIN_TOOLS (плюс всё из PUBLIC_TOOLS, только если вызывающий — админ):**
| Инструмент | Аргументы | Реализация |
|---|---|---|
| `add_trigger_word` | `word: str` | `repository.add_trigger_word` |
| `delete_trigger_word` | `word: str` | `repository.delete_trigger_word` |
| `reset_user_warnings` | — (цель из reply, обязателен) | `repository.reset_warning` |
| `mute_user` | `minutes: int` | (цель из reply, обязателен + подтверждение) `moderation/actions.py::mute_user` (новый) |
| `kick_user` | — | (цель из reply, обязателен + подтверждение) `moderation/actions.py::kick_user` (новый) |
| `set_reset_days` | `days: int` | `repository.set_reset_days` |
| `set_broadcast_interval` | `minutes: int` | `repository.set_broadcast_interval` + `schedule_chat_broadcast` |
| `add_broadcast_message` | `text: str` | `repository.add_broadcast_message` |
| `delete_broadcast_message` | `message_id: int` | `repository.delete_broadcast_message` |
| `set_warn_message` | `text: str` | `repository.set_warn_message` |
| `set_mute_message` | `text: str` | `repository.set_mute_message` |
| `set_kick_message` | `text: str` | `repository.set_kick_message` |
| `reset_punishment_messages` | — | `repository.reset_message_templates` |

Все инструменты, которым нужна цель (`get_user_warnings`, `reset_user_warnings`, `mute_user`, `kick_user`), **не принимают аргумент "кого"** — цель всегда берётся из `message.reply_to_message`, модель не может её указать текстом. Если reply отсутствует, инструмент не вызывается вообще (код перехватывает это до исполнения), бот просит ответить на нужное сообщение.

### Подтверждение для mute/kick

Отдельная логика (не через текстовый "да"/"нет", а через inline-кнопки — надёжнее, чем парсить свободный текст):

1. Модель запрашивает `mute_user`/`kick_user` → бот сохраняет "отложенное действие" в памяти (`dict[token, PendingAction]`, где `PendingAction` = admin_user_id, chat_id, action type, target_user_id, target_mention, minutes) и шлёт сообщение с двумя кнопками (callback_data вида `aiconfirm:{token}:yes` / `aiconfirm:{token}:no`).
2. По нажатию кнопки: если нажал не тот админ, что вызвал `/ask` — игнорировать (или ответить alert "не твоё решение"). Если "yes" — выполнить действие через `moderation/actions.py`, отредактировать сообщение с результатом. Если "no" — отредактировать сообщение как "отменено".
3. Отложенные действия живут только в памяти процесса (как и троттлинг уведомлений о правах) — переживать перезапуск бота не обязаны.

### Новый модуль `moderation/actions.py`

Мьют/кик через ИИ — это НЕ то же самое, что мьют/кик за нарушение триггер-слова (там есть эскалация счётчика, тут — прямое действие по просьбе админа, без изменения счётчика предупреждений). Поэтому логика выносится в отдельные, переиспользуемые функции, не трогая существующий `moderation/handlers.py`:

```python
async def mute_user(bot: Bot, chat_id: int, user_id: int, minutes: int) -> bool  # True = успех
async def kick_user(bot: Bot, chat_id: int, user_id: int) -> bool  # True = успех, ban+unban
```

Обе ловят `TelegramAPIError` (нехватка прав у бота) и возвращают `False` вместо исключения — вызывающий код сам решает, что ответить.

### Regex hard-filter (`ai/content_filter.py`)

```python
def check_hard_block(text: str) -> bool
```

Паттерны (RU + EN, case-insensitive), одна категория "попытка манипуляции ассистентом":
- `игнорируй (все )?(предыдущие )?инструкции`, `забудь (свои )?(правила|инструкции)`
- `ты (теперь|отныне)? в режиме (разработчика|debug|developer)`
- `покажи (мне )?(системн\w* промпт|system ?prompt)`
- `притворись,? что ты (админ|администратор|admin)`
- `ignore (all )?(previous )?instructions`, `you are now (unrestricted|jailbroken|in developer mode)`, `reveal (your )?system prompt`

При совпадении — ответ "Не могу выполнить этот запрос." без обращения к OpenRouter (проверяется первым шагом в `cmd_ask`, до построения списка инструментов и до сетевого вызова — то есть без затрат токенов).

### Расширение `ai/openrouter_client.py`

Новая функция `ask_ai_with_tools(question: str, tools: list[dict]) -> AIResponse`, где:

```python
@dataclass
class AIResponse:
    text: Optional[str]              # если модель просто ответила текстом
    tool_name: Optional[str]         # если модель запросила вызов инструмента
    tool_arguments: dict             # аргументы вызова (уже распарсенный JSON)
```

Отправляет `tools` в теле запроса (`tools`, `tool_choice: "auto"`), парсит `choices[0].message` — либо `content` (текст), либо `tool_calls[0]` (берём только первый вызов, если модель вернула несколько — сознательное упрощение для первой версии). Ошибки — та же `AIUnavailableError`, что и сейчас.

## Тестирование

- `content_filter.py` — юнит-тесты на срабатывание/несрабатывание паттернов.
- `moderation/actions.py` — тесты с моком `Bot` (аналогично существующим тестам на restrict/ban).
- Инструменты — по одному тесту на каждый: выполняется с реальным `Repository` (tmp_path SQLite), мок только на `Bot`.
- Оркестрация `cmd_ask` — тесты на: hard-filter блокирует до вызова ИИ; обычный пользователь не получает admin-инструменты (мокаем `ask_ai_with_tools`, проверяем, какой список `tools` ему передали); инструмент с обязательной целью без reply не вызывается; mute/kick уходят в подтверждение, а не выполняются сразу; подтверждение от чужого пользователя игнорируется.
- Реальный сквозной прогон с настоящим OpenRouter — только вручную (как и раньше, автотестами LLM не покрывается).

## Границы (сознательно не делаем сейчас)

- Не расширяем набор slash-команд (pin/unpin, lock, инвайт-ссылки и т.п.) — отдельная будущая задача.
- Не поддерживаем несколько вызовов инструментов за один ответ модели — берём первый.
- Не логируем и не сохраняем историю диалога с ИИ между сообщениями — каждый `/ask` независим (как сейчас).
- Не даём модели никакого доступа к содержимому `.env`/токенам — это в принципе невозможно, они никогда не передаются в промпт.
