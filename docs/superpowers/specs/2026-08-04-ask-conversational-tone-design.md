# Живое общение в `/ask` + фикс подчёркиваний в именах команд — дизайн

## Контекст

Сейчас `SYSTEM_PROMPT` в `ai/openrouter_client.py` построен как инструкция технического маршрутизатора: сначала описывает три служебные функции (`read_tools_reference`, `read_general_info`, `call_tool`) и правила их вызова, и только потом, вскользь, разрешает отвечать текстом. На практике это приводит к двум наблюдаемым проблемам (из реальных диалогов в чате):

1. **Открытое обсуждение трактуется как команда.** На вопрос «насчёт этого списка [триггер-слов] можно ли ещё добавить какие-то слова или этого достаточно?» — это приглашение обсудить/посоветоваться — бот вместо ответа своими словами вызвал `read_tools_reference` и вывалил пользователю сырой технический каталог всех команд бота. Причина: правило в промпте «если нужно выполнить модерационное действие (мьют, кик, **триггер-слово и т.п.**) — сначала `read_tools_reference`» слишком широкое — упоминания темы «триггер-слово» достаточно, чтобы уйти в технический путь, даже когда пользователь не просил ничего добавлять/удалять.
2. **Имена команд теряют подчёркивания при отправке.** Промпт просит модель оборачивать имена вида `add_trigger_word` в обратные кавычки (чтобы Telegram-Markdown не тронул `_`), но модель это не всегда делает. Без кавычек `parse_mode="Markdown"` (legacy) трактует `_trigger_` как маркер курсива и вырезает оба символа `_` из отображаемого текста, превращая `list_trigger_words` в `listtriggerwords`, `add_trigger_word` в `addtriggerword` и т.д. — весь список команд получился нечитаемым.

Запрос пользователя: сделать общение в `/ask` неформальным, «как с друзьями» (не сухо-технически), сохранив при этом рабочий вызов инструментов, когда пользователь явно просит выполнить действие. Плюс — устранить конкретный баг с подчёркиваниями, увиденный в примере.

## Область

- Меняется только `SYSTEM_PROMPT` (текст) и добавляется пост-обработка текстового ответа модели перед отправкой в Telegram.
- Логика выбора и исполнения инструментов (`ask_ai_with_tools`, `META_TOOLS`, `execute_tool`, проверки прав в `ai/handlers.py`) не меняется — это чисто фикс промпта и форматирования.
- `/setpersona` (существующий механизм, `docs/superpowers/specs/2026-08-03-chat-persona-design.md`) не трогаем — он по-прежнему добавляется поверх `SYSTEM_PROMPT` и может донастроить тон дальше сверху для конкретного чата.

## Новый `SYSTEM_PROMPT`

```python
SYSTEM_PROMPT = (
    "Ты — участник этого Telegram-чата, отвечаешь на вопросы по команде /ask. "
    "Общайся неформально и по-дружески, как обычный собеседник в переписке (в духе "
    "ChatGPT/Claude/Gemini), а не как техническая справочная система: живо, коротко по "
    "делу, без канцелярита, можно шутить в тон. Если пользователь спрашивает твоё мнение, "
    "зовёт что-то обсудить или посоветоваться — отвечай от себя своими словами, а не "
    "сухим перечислением.\n\n"
    "За кулисами (пользователь про них не знает и сам их не называет) у тебя есть три "

    "аргументами; read_general_info() — информация о боте, разработчике, логике "
    "модерации и текущих настройках этого чата; call_tool(name, arguments) — выполнение "

    "спрашивает про твои возможности/бота/настройки: «что ты умеешь», «какие есть "

    "настройки чата → read_general_info; явная просьба выполнить модерационное действие "
    "(замьютить, кикнуть, добавить/удалить триггер-слово и т.п.) → сначала "

    "Если пользователь не просит действие, а рассуждает или советуется на тему "

    "именно сделать. То же самое с простым приветствием («привет», «здарова» и т.п.), "
    "благодарностью или репликой не по делу — просто ответь в тон, без вызова "
    "инструментов и без перечисления своих возможностей по собственной инициативе.\n\n"
    "Результат read_general_info и read_tools_reference — справочные данные для тебя, а "
    "не готовый ответ: после получения отвечай кратко и по существу вопроса своими "
    "словами, не копируя и не пересказывая инструмент целиком, если явно не просили "
    "полную информацию обо всём сразу. Если в сообщении несколько разных вопросов — "
    "ответь на каждый из них, вызвав все нужные инструменты по очереди, прежде чем дать "
    "финальный ответ. Если вопрос можно закрыть, выполнив доступную команду (например "
    "list_trigger_words, чтобы показать реальный список слов) — вызови её через "
    "call_tool и покажи результат, а не объясняй пользователю, как вызвать команду "
    "самому.\n\n"
    "При вызове add_trigger_word никогда не подставляй шаблонные плейсхолдеры вида "

    "отдельным элементом списка.\n\n"
    "Ответ форматируется как Markdown: имена инструментов и команд (например, "

```

Все прежние функциональные правила сохранены (плейсхолдеры в `add_trigger_word`, ответ на каждую часть составного вопроса, запрет пересказывать инструмент целиком, «не вызывай инструменты на голое приветствие», обёртка имён в бэктики) — просто переставлены так, что личность/тон идёт первым, а не тонет под техническими правилами, и добавлена новая явная граница «обсуждение/мнение → текст, без тула».

## Программный фикс подчёркиваний

Не полагаемся только на то, что модель вспомнит обернуть имя в бэктики — подстраховываем кодом в `ai/handlers.py`:

```python
import re

_TOOL_NAME_PATTERN = re.compile(
    r"(?<!`)\b("
    + "|".join(re.escape(name) for name in sorted(ADMIN_TOOL_NAMES, key=len, reverse=True))
    + r")\b(?!`)"
)


def _wrap_tool_names(text: str) -> str:
    return _TOOL_NAME_PATTERN.sub(r"`\1`", text)
```

Применяется в `cmd_ask` к текстовому ответу модели перед отправкой:

```python
if response.tool_name is None:
    text = _wrap_tool_names(response.text or UNAVAILABLE_MESSAGE)
    try:
        await message.answer(text, parse_mode="Markdown")
    except TelegramBadRequest:
        await message.answer(text, parse_mode=None)
    return
```

`ADMIN_TOOL_NAMES` — надмножество всех имён (включает `PUBLIC_TOOL_NAMES`), поэтому фикс работает одинаково для админов и не-админов, даже если модель вслух упомянула админский тул в разговоре с обычным пользователем (сам вызов всё равно заблокирован проверкой прав в `cmd_ask` — это не меняется).

`(?<!`)...(?!`)` — не задваивает кавычки, если модель сама уже обернула имя. `\b` на границах — не трогает имя, если оно часть более длинного идентификатора (например `mute_user_id`), хотя таких случаев в кодовой базе нет.

Добавить новый тест на границу «обсуждение vs действие» (что в промпте прямо есть инструкция не вызывать тул при рассуждении/совете).
- Новые unit-тесты на `_wrap_tool_names` (скорее всего в `tests/test_ai_handlers.py`, рядом с остальными тестами `cmd_ask`):
  - имя без кавычек (`list_trigger_words`) → оборачивается в бэктики;
  - имя, уже в бэктиках, → не дублируется;
  - текст без упоминаний известных имён → не меняется;
  - несколько разных имён в одном тексте → оборачиваются все.
- Интеграционный тест на `cmd_ask`: `AIResponse(text="... list_trigger_words ...")` без `tool_name` → в отправленном сообщении имя обёрнуто в бэктики.

## Границы (сознательно не делаем)

- Не убираем инструменты из запроса эвристикой/классификатором (вариант B из обсуждения) — усложнение непропорционально задаче, промпт-фикса достаточно для наблюдаемых кейсов.
- Не переходим на `MarkdownV2` с полным экранированием — это отдельная, более инвазивная задача (нужно экранировать все спецсимволы в произвольном тексте модели), а конкретная проблема — только с именами инструментов, которую целевой regex-фикс закрывает точечно.
- Не меняем модель (`meta-llama/llama-3.3-70b-instruct` через OpenRouter) и не добавляем pinning провайдера — не входит в эту задачу.
- Не трогаем `/setpersona` и его текст — по-прежнему добавляется поверх `SYSTEM_PROMPT` как есть.
